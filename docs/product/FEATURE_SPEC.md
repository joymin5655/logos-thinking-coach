## 0. 읽는 법

### 0.1 범위와 근거
- 구조는 요구사항 R1~R9 → 기능 Rn-Fm → 상세 기능 Rn-Fm-Dk다. 다른 문서는 이 ID로 참조한다.
- "구현됨"은 `claude-ux-uplift` 워크트리(커밋 01c7084)의 코드를 읽고 확인한 것만 적었다. 이 워크트리는 이후 main에 머지되었다(15f2ee0, #2). 머지본과의 차이는 판정 규칙(`verdictOf`), 아레나 주제 6개, 코칭 예시 버튼만 다시 확인했고 나머지는 재확인하지 않았다. 경로는 저장소 루트 기준이다.
- "계획(Phase 2)"은 2026-10-13 사용자 결정(KPI 계측·파일럿 검증·성장 UI)에 따른 설계 제안이다. 구현은 브랜치 `claude/retention-kpi`에 있고(PR 대기, 운영 미배포) 머지 전이라 상태 라벨은 "계획"으로 둔다. 목업과의 차이 9건(IA_SCREENS §4.9 M1~M9)은 2026-10-13 사용자 위임으로 모두 결정됐고, 이 문서에 반영했다. 이름·수치 중 "(안)"이라고 적은 것은 확정 전이다. 미정이던 4개 항목은 2026-10-13 사용자 위임으로 기본값을 확정했다("기본값으로 결정"이라고 표기).
- "제외"는 이번 범위에서 만들지 않기로 한 것이다(웹 푸시, 결제, 사용자 간 아레나, B2B 문서 검증).
- 코드로 확인하지 못한 것은 "미확인", 코드에 처리가 없는 것은 "미처리(갭)"로 적었다. 갭은 마지막 섹션에 모았다.

### 0.2 용어
- 비회원: 로그인하지 않은 사용자. 회원: Google 로그인한 사용자. 관리자: `private.admins`에 등록된 계정.
- 세션: 코칭 세션(`kind='session'`). 판: 아레나 1회. 논증: 오늘의 논증(`kind='argue'`).
- sid: 세션·판·진단 1건의 uuid. 이용 한도는 sid 단위로 센다.
- 루브릭: 일관성 30(0/15/30) + 근거 구체성 40(0/20/40) + 방어력·메타인지 30(0/15/30) = 100점. 모든 점수는 AI 추정치다(`server/logos/prompts.ts` RUBRIC).
- 하루: 한국 시간(KST) 자정 기준(`consume_quota`).

### 0.4 공통 예외 처리 (E1~E11)
기능 블록의 "예외"는 이 번호를 인용하고, 기능별 차이만 덧붙인다. 클라이언트 매핑은 `client/src/lib/api.ts`, 서버는 `server/logos/handler.ts`·`guard.ts`·`quota.ts`다.

| ID | 상황 | 실제 처리 |
|---|---|---|
| E1 | 401 `auth` (토큰 없음·만료·4KB 초과·삭제된 계정) | `handleAuthError`가 쓰던 글을 초안으로 저장하고 `/login?next=<현재 경로+쿼리>`로 보낸다. 로그인 후 같은 경로로 돌아오고 초안이 복원된다(`useDraft`). 진행 중 기록은 이미 로컬에 있다. |
| E2 | 429 `quota` (`reason`: `day`·`refs`·`ref_calls`) | `ErrorLine`이 "오늘 한도를 다 썼어요 · 내일 다시 이용할 수 있어요"와 `/dashboard/subscription` 링크를 보여 준다. `reason`은 클라이언트에서 쓰지 않는다(갭 G3). **계획(Phase 2, 2026-10-13 결정)**: 비회원 진단의 한도 초과는 "내일 다시" 대신 "로그인하면 계속할 수 있어요" 안내와 로그인 버튼을 보인다(R1-F1). |
| E3 | 429 `rate` (IP당 10분 60회 초과) | "요청이 너무 많아요" + 다시 시도 버튼. 인스턴스 메모리 기준 best-effort. |
| E4 | 502 `upstream` (Anthropic 오류·거절·`max_tokens`·파싱 실패) | "AI 응답을 받지 못했어요" + 다시 시도. 원인 구분 없음(갭 G4). 본문·헤더는 로그에 남기지 않는다. |
| E5 | 503 `unavailable` (API 키·Supabase 미설정, 한도 RPC 장애·5초 타임아웃) | "서비스를 준비 중이에요". |
| E6 | 클라이언트 55초 초과 / 네트워크 끊김 | `timeout`·`network` 코드. 서버는 Anthropic 25초 타임아웃 + 재시도 1회, 함수 `maxDuration` 60초. |
| E7 | 400 `bad_request` (스키마 위반, JSON 아님, 405, 415), 413 (본문 64KB 초과) | "입력을 처리하지 못했어요. 내용을 조금 줄이거나 다시 써 보세요". |
| E8 | 403 `origin` (허용 목록에 없는 Origin/Referer) | "이 주소에서는 사용할 수 없어요". |
| E9 | 오프라인 | AI 호출은 E6으로 실패한다. 기록 열람·로컬 저장은 계속된다. 회원 기록은 outbox에 쌓이고 `online` 이벤트·탭 숨김 때 재전송한다. 사용자 메뉴에 "미동기화 N건" 표시. |
| E10 | 비회원이 보호 라우트 접근 | `RequireAuth`가 `/login?next=<경로+쿼리>`로 보낸다. 로그인 후 `next`로 돌아온다. 공개 라우트는 R6-F1에 있다. |
| E11 | 로그인 오류 | 시작 실패 "로그인을 시작하지 못했어요", 콜백에서 15초 안에 세션이 안 잡히면 오류 카드 + "다시 로그인", Supabase 미설정은 "로그인 준비 중이에요". (R6-F1 예외와 같다.) |

공통 사실:
- 한도 차감은 LLM 호출 **전**에 일어난다. E4~E6으로 실패해도 호출 1회가 차감된다(갭 G2).
- 재시도는 같은 sid로 보내므로 "판 수"는 늘지 않고 "sid당 호출 수"만 늘어난다.
- 입력 상한: 메시지·답 1,000자, 주제 200자, 논증 이유 500자, 최종 정리 1,500자, 진단 답안 2,000자.

## R1. 진단·기준점

### R1-F1 3분 진단 응시
- **누가-왜-무엇을**: 처음 온 사용자(비회원 포함)가 현재 논리력의 기준점을 만들려고, 문항 하나에 3분 안팎으로 짧은 논증을 쓴다.
- **선행 조건 / 트리거**: 선행 없음. `/dashboard/diagnostic`은 공개 라우트다(`App.tsx`). 첫 진단이 없으면 홈에 초대 줄이 뜨고(건너뛰기 가능), 랜딩·홈 외에도 직접 URL로 진입할 수 있다.
- **정상 결과**
  1. 문항 하나가 보인다. 문항은 4개(`prompt0~3`)를 `진단 횟수 % 4`로 순환한다.
  2. 180초 타이머가 돈다. 0이 되면 "초과"로 표시만 하고 입력은 막지 않는다.
  3. 30자 이상 쓰면 "채점" 버튼이 켜진다(최대 2,000자).
  4. `score`(kind=`diagnostic`)를 호출한다. 응답은 일관성·근거·방어력·총점·근거 문장이다.
  5. 결과를 로컬에 저장하고(`addDiagnostic` → 오늘을 활동일로 기록) R1-F2 화면으로 바뀐다.
- **예외 처리**
  - 30자 미만: 버튼 비활성 + "최소 30자" 안내.
  - 비회원 하루 3회 초과(IP, 서버 메모리): 429 `quota` → E2. 현재는 서버 메시지("로그인하면 계속할 수 있어요")를 쓰지 않고 "내일 다시"와 구독 링크가 나온다(갭 G3). **계획(Phase 2, 2026-10-13 결정)**: 서버 메시지를 쓰는 로그인 유도로 바꾼다(문구와 버튼 `/login?next=/dashboard/diagnostic`은 가안).
  - 401(회원 토큰이 무효): E1. 쓰던 글은 `essay` 초안으로 복원.
  - 429 rate, 502, 503, 타임아웃, 오프라인: E3~E6, E9. 오류 줄의 "다시 시도"는 같은 sid·같은 글로 재요청한다(진단은 sid당 2회까지 허용).
  - 문항 id를 기록에 남기지 않고 문항 본문만 저장한다(갭 G6).
- **데이터 출처·저장**: 로컬 `logos.v1.diagnostics[]`(`id=sid, at, prompt, text, score`). 회원이면 `records`(kind=`diagnostic`, `started_at=completed_at=at`, `score_after=총점`, `data=기록 전체`). API `score`.
- **권한**: 비회원 가능(서버 검증은 IP 한도뿐이며, 점수 서버 검증은 하지 않는 것으로 기본값 결정, 2026-10-13). 회원 가능.
- **상태 유지**: 작성 중 글은 sessionStorage 초안에 400ms 디바운스로 저장되고 새로고침 후 복원된다. 타이머는 복원하지 않는다(재진입 시 180초부터).
- **정책**: 회원은 진단 하루 2판·판당 2호출(`QUOTAS.diagnostic`). 비회원은 IP당 하루 3회(`GUEST_DIAGNOSTICS_PER_DAY`). 회원 일 전체 호출 상한 100(`DAILY_CALL_CEILING`).
- **수용 기준**
  - 사용자는 로그인하지 않고도 진단 답안을 써서 점수를 받을 수 있다.
  - 사용자는 타이머가 끝나도 글을 계속 쓰고 제출할 수 있다.
  - 사용자는 30자 미만이면 제출할 수 없고 이유를 안내받는다.
  - 사용자는 채점 실패 시 쓴 글을 잃지 않고 같은 화면에서 다시 시도할 수 있다.
  - 사용자는 401로 로그인 화면에 다녀와도 쓰던 글을 되찾는다.
  - (계획) 비회원이 한도를 넘으면 로그인하면 계속할 수 있다는 안내와 로그인 버튼을 본다.
- **코드 경로**: `client/src/pages/Diagnostic.tsx`, `client/src/lib/store.ts`(addDiagnostic), `client/src/lib/draft.ts`, `server/logos/handler.ts`(score).

### R1-F4 진단 문항 교차 출제
- **누가-왜-무엇을**: 파일럿 참가자가 사전·사후 진단에서 같은 문항을 풀지 않도록, 문항 풀을 둘로 나누어 교차 출제한다. 문항 난이도 편향과 연습 효과를 줄이는 것이 목적이다.
- **선행 조건 / 트리거**: R7-F6으로 군에 배정된 참가자의 첫·재진단. 비참가자는 지금의 순환을 유지한다.
- **정상 결과**
  1. 진단 문항에 안정적 식별자(`promptId`)를 붙이고, 기록에 `promptId`를 함께 저장한다.
  2. 첫 진단은 풀 X, 재진단은 풀 Y에서 낸다. X/Y 순서는 참가자마다 균형을 맞춘다(안: `user_id` 해시의 홀짝).
  3. 이미 푼 `promptId`는 같은 참가자에게 다시 내지 않는다.
- **예외 처리**: 문항 풀이 소진되면 가장 오래 전에 푼 문항을 허용하고 기록에 `repeat=true`를 남긴다(안). 기존 기록에 `promptId`가 없으면 문항 본문 비교로 대체한다(언어가 달라 일치하지 않을 수 있음).
- **데이터 출처·저장**: `diagnostics[].promptId`(신규 필드, `records.data`에 포함). 풀 정의는 클라이언트 상수(문항 본문은 i18n). 별도 테이블 없음.
- **권한**: 참가자(회원). 비회원은 적용하지 않는다.
- **상태 유지**: 순서는 계산으로 재현되므로 별도 저장하지 않는다(안).
- **정책**: 풀 크기와 문항 수(현재 4개 → 최소 풀당 2개 이상 필요)는 미정. 블라인드 채점 export(R7-F7)의 `form`은 `promptId`를 쓴다.
- **수용 기준**
  - 사용자는 재진단에서 첫 진단과 다른 문항을 받는다.
  - 사용자는 언어를 바꿔도 같은 문항을 다시 받지 않는다.
  - 운영자는 export에서 문항 식별자로 채점 결과를 묶을 수 있다.
- **코드 경로**: (신규) `Diagnostic.tsx`의 문항 선택부, `lib/store.ts`(DiagnosticRecord).
- **상태**: 계획(Phase 2)

## R2. 깊은 코칭 세션

### R2-F1 코칭 시작(주제 입력·예시)
- **누가-왜-무엇을**: 결정을 앞뒀거나 주장을 점검하려는 로그인 사용자가 고민 주제를 한 줄 적어 코칭을 시작한다.
- **선행 조건 / 트리거**: 로그인. `/dashboard/session` 진입(사이드바·하단 탭·랜딩 CTA).
- **정상 결과**
  1. 인트로에서 주제를 입력한다(최대 200자). 예시 버튼 4개(고민·결정·주장 2)를 누르면 입력칸에 채워진다.
  2. Enter(데스크톱) 또는 "시작" 버튼으로 시작한다. 터치 기기에서는 Enter가 줄바꿈이다.
  3. 고정 첫 질문("이 주제에서 지금 가장 확신하는 한 가지는 무엇인가요?")이 클라이언트에서 바로 나온다(API 호출 없음).
- **예외 처리**
  - 비회원: 보호 라우트라 `/login?next=/dashboard/session`으로 이동한다(`RequireAuth`).
  - 한도가 이미 소진된 날: 시작 시점에는 알 수 없고 첫 답을 보낼 때 E2가 난다(갭 G3).
  - 한글 조합 중 Enter는 무시한다.
- **데이터 출처·저장**: 시작만으로는 저장하지 않는다. 첫 사용자 답이 생기면 `sessions[]`에 `kind='session'`으로 저장한다(시작만 하고 떠난 세션이 완주율 분모를 부풀리지 않게 하기 위함).
- **권한**: 회원.
- **상태 유지**: 주제만 쓰고 떠나면 사라진다(첫 답 이전은 저장하지 않음). 입력 중 글은 초안에 보관되지만 주제 입력칸은 초안 슬롯이 없다(미확인: 주제칸에 `useDraft` 연결 없음).
- **정책**: 세션 하루 2판, 판당 API 호출 32회(`QUOTAS.session`).
- **수용 기준**
  - 사용자는 예시를 눌러 주제를 빠르게 채울 수 있다.
  - 사용자는 주제를 200자까지 입력해 코칭을 시작할 수 있다.
  - 사용자는 시작하자마자 AI 대기 없이 첫 질문을 볼 수 있다.
  - 사용자는 첫 질문에 직접 쓴 답이 이후 모든 질문의 기준점(anchor)이 됨을 안다.
- **코드 경로**: `client/src/pages/ThinkingSession.tsx`(intro, startSession), `client/src/i18n/ko/session.ts`.
- **상태**: 구현됨
- **R2-F1-D1 예시 버튼(= "예시 칩")**: 4개 모두 i18n 문구(`exampleLabel` "이렇게 시작해 보세요")이며 입력칸을 채우기만 한다. 시작하지 않는다. PRD·USER_FLOWS·IA_SCREENS가 "코칭 시작 칩"·"예시 칩"이라 부르는 요소와 같다고 판단한다(코드에 "chip"이라는 이름의 요소는 없다. 같은 요소라는 판단은 화면 문구와 동작 비교에 따른 것이다).

### R2-F2 4단계 코칭 대화
- **누가-왜-무엇을**: 코칭 중인 사용자가 답을 받지 않고, 질문만으로 표면 → 도전 → 핵심 → 통합 순서로 생각을 파고든다.
- **선행 조건 / 트리거**: R2-F1에서 첫 답(anchor)을 보낸다. 이후 답을 보낼 때마다 `session.turn`을 호출한다.
- **정상 결과**
  1. 사용자 답이 로컬에 먼저 저장되고(회원은 outbox에 올라감) `session.turn`을 호출한다.
  2. 서버가 질문 1개와 단계(`stage`), 유형(`detectedType`), 혼란 여부(`aporia`)를 돌려준다.
  3. 서버가 단계를 보정한다: 뒤로 가지 않고, 한 번에 최대 한 단계 앞선다. 사용자 답 2회마다 최소 한 단계 올린다(`paceStage`). 혼란이거나 THINK이면 올리지 않는다.
  4. 질문과 단계 태그가 대화에 붙고, 오른쪽(모바일은 아래) 진행 막대가 갱신된다.
  5. 통합 단계 질문에 답했거나 사용자 답이 6회 이상이면 "정리하기"가 켜진다.
- **예외 처리**
  - E1~E8 모두 해당한다. 실패하면 방금 보낸 답은 대화에 남고 "마지막 답 다시 보내기" 줄이 뜬다. 입력창과 재시도 버튼에 같은 글이 이중으로 남지 않게 정리한다.
  - 모델이 거절·잘림·파싱 실패하면 502(E4).
  - 위기 신호(의료·법률·자해): 프롬프트가 코칭을 멈추고 전문 도움을 권하는 한 문장만 쓰게 한다. 화면 안내·로그·후속 처리는 없다(갭 G7).
  - "그냥 알려줘" 요청: 프롬프트가 이유를 한 문장으로 밝히고 질문으로 돌려주게 한다. 서버가 준수 여부를 검증하지는 않는다.
  - `detectedType`은 응답에 오지만 저장·표시하지 않는다.
- **데이터 출처·저장**: 로컬 `sessions[].turns[]`(역할·내용·시각·단계·신호·aporia), `anchor`, `firstClaim`, `stageReached`, `promptVersion`. 회원은 `records`(kind=`session`)에 upsert. API `session.turn`(모델 `claude-sonnet-5-5`, effort low, 출력 1,200토큰, 질문 600자로 절단).
- **권한**: 회원.
- **상태 유지**: 사용자 턴마다 저장되므로 이탈해도 R2-F5로 이어진다. 입력 중 글은 초안으로 보관된다.
- **정책**: 서버에 보내는 history는 최근 16턴, 각 1,000자. 판당 호출 32회 이내(턴 + 첫 주장 채점 + 최종 채점 2 + 리포트 + 재시도).
- **수용 기준**
  - 사용자는 질문에 답하며 4단계 중 현재 위치를 진행 막대로 볼 수 있다.
  - 사용자는 AI가 답이 아니라 질문만 한다는 것을 대화 내내 경험한다.
  - 사용자가 보내기 전에 쓴 글은 전송이 실패해도 보존된다.
  - 사용자는 충분히 진행하면 "정리하기"를 누를 수 있다.
- **코드 경로**: `ThinkingSession.tsx`(runTurn), `server/logos/handler.ts`(`nextStage`, `paceStage`, `clampStage`), `server/logos/prompts.ts`(SESSION_SYSTEM), `server/logos/schemas.ts`.
- **상태**: 구현됨

### R2-F3 신호 버튼(파고들기·마치기·혼자 생각)
- **누가-왜-무엇을**: 코칭 중인 사용자가 대화의 속도와 방향을 직접 조절하려고 세 가지 신호를 보낸다.
- **선행 조건 / 트리거**: 첫 답(anchor) 이후 활성화된다. 버튼 3개(화면 문구): "더 파고들어줘"(DEEPEN), "이 정도면 됐어"(ENOUGH), "내가 더 고민해볼게"(THINK).
- **정상 결과**
  1. 버튼을 누르면 입력칸의 글(없으면 버튼 라벨)이 `[CONTROL:신호]`와 함께 전송된다.
  2. DEEPEN은 같은 지점을 더 압박하는 질문, ENOUGH는 최소 한 단계 진행, THINK는 단계를 올리지 않고 붙들 질문 하나만 남긴다.
  3. THINK 후 "저장하고 나가기 / 계속하기" 카드가 뜬다. 저장하고 나가면 토스트 후 홈으로 가며 R2-F5로 이어진다.
- **예외 처리**: 첫 답 전에는 비활성(안내 문구 표시). 로딩 중 비활성. 전송 실패는 R2-F2와 같고 신호도 재시도에 함께 유지된다. 모바일(≤640px)에서는 입력창 위 한 줄 버튼으로 바뀐다.
- **데이터 출처·저장**: 사용자 턴의 `control` 필드. API `session.turn.control`.
- **권한**: 회원.
- **상태 유지**: 신호는 턴에 남아 기록 상세에서 태그로 보인다.
- **정책**: 신호 사용 횟수 제한 없음. ENOUGH로 단계는 올라가지만 "정리하기" 활성 조건(통합 단계 응답 또는 답 6회)은 별도다.
- **수용 기준**
  - 사용자는 한 번의 탭으로 더 깊이 묻기, 마무리하기, 생각할 시간 갖기를 선택할 수 있다.
  - 사용자는 "혼자 생각할게요" 뒤 저장하고 나가 나중에 이어서 할 수 있다.
  - 사용자는 모바일에서도 입력창 바로 위에서 신호를 보낼 수 있다.
- **코드 경로**: `ThinkingSession.tsx`(send, controlsRow), `handler.ts`(nextStage의 control 처리).
- **상태**: 구현됨

### R2-F4 Recovery(혼란 감지)
- **누가-왜-무엇을**: 막혀서 "모르겠다"고 답한 사용자가 포기하지 않도록, 코치가 처음 확신했던 지점으로 돌아가 더 작은 질문을 한다.
- **선행 조건 / 트리거**: 모델이 응답에서 `aporia=true`를 낸다(짧은 답, 모르겠다, 앞뒤 모순).
- **정상 결과**
  1. 해당 AI 턴에 점선 테두리와 "Recovery" 표시가 붙는다.
  2. 질문은 ① 막혔음을 인정 ② anchor로 복귀 ③ 훨씬 작은 질문 하나 순서로 구성하도록 프롬프트가 지시한다.
  3. 서버는 이 턴에서 단계를 올리지 않는다.
- **예외 처리**: 혼란 판정은 모델 판단이며 서버·클라이언트에 별도 검증이 없다. 판정이 틀려도 사용자 조치는 없다.
- **데이터 출처·저장**: 턴의 `aporia` 필드(로컬·`records.data`).
- **권한**: 회원.
- **상태 유지**: 기록에 남는다.
- **정책**: 지표로 집계하지 않는다(Recovery 발생률 미집계).
- **수용 기준**
  - 사용자는 막혔을 때 더 쉬운 질문으로 되돌아가는 경험을 한다.
  - 사용자는 Recovery 턴을 일반 턴과 구분해 볼 수 있다.
- **코드 경로**: `server/logos/prompts.ts`(SESSION_SYSTEM), `handler.ts`(hold), `ThinkingSession.tsx`.
- **상태**: 구현됨

### R2-F5 세션 이어하기
- **누가-왜-무엇을**: 중간에 나간 사용자가 같은 세션을 이어가려고 이전 대화를 복원한다.
- **선행 조건 / 트리거**: 사용자 답이 1회 이상 있고 완료되지 않은 가장 최근 코칭 세션. 코칭 인트로의 "이어서" 줄 또는 홈 이어하기 카드(`/dashboard/session?resume=<id>`).
- **정상 결과**
  1. 주제·대화·anchor·정리 초안이 복원되고 세션 단계로 들어간다.
  2. 마지막 저장 턴이 사용자 턴이면(답을 못 받고 끊김) 재시도 상태로 복원되어 "다시 보내기"가 뜬다.
  3. 다른 기기에서도 동기화(R6-F2)로 받은 기록이면 이어갈 수 있다.
- **예외 처리**: 이어갈 세션이 없으면 줄이 보이지 않는다. 논증·아레나는 이어갈 수 없다(갭 G1). 정리 화면에서 나갔다면 정리 화면이 아니라 대화 화면으로 복원된다.
- **데이터 출처·저장**: `sessions[]`에서 선택(`pickResume`). 단계는 마지막 AI 질문의 단계.
- **권한**: 회원.
- **상태 유지**: 이 기능이 곧 상태 유지다. 복원되는 것은 저장된 턴·anchor·정리 글이며, 화면 phase는 복원하지 않는다.
- **정책**: 이어하기 대상은 세션 1건(가장 최근)이다. 오래된 미완료 세션의 만료 정책은 없다(갭 G1).
- **수용 기준**
  - 사용자는 홈에서 한 번의 탭으로 중단한 세션 단계에서 이어갈 수 있다.
  - 사용자는 답을 못 받고 끊긴 마지막 답을 다시 보낼 수 있다.
  - 사용자는 다른 기기에서도 이어갈 수 있다.
- **코드 경로**: `client/src/lib/resume.ts`, `ThinkingSession.tsx`(resume), `DashboardHome.tsx`.
- **상태**: 구현됨

### R2-F6 최종 정리·채점·리포트
- **누가-왜-무엇을**: 대화를 마친 사용자가 자기 말로 결론을 쓰고, 처음 주장과 비교한 점수 변화와 빈틈 리포트를 받는다.
- **선행 조건 / 트리거**: "정리하기" 활성(통합 단계 응답 또는 답 6회). 정리하기 버튼 → 정리 화면.
- **정상 결과**
  1. 처음 주장을 인용으로 보여 주고, 지금의 생각을 30자 이상 1,500자 이하로 직접 쓰게 한다.
  2. 제출하면 정리 글을 저장한 뒤 병렬로 호출한다: 처음 주장 채점(없을 때만), 정리 채점, `session.report`.
  3. 셋 다 성공하면 완료(`completedAt`)로 저장하고 오늘을 활동일로 기록한다.
  4. 완료 화면에 Before→After 점수(Δ), 처음/마지막 인용, 항목별 막대("AI 추정치" 근거), 리포트(막힌 지점 3, 전제 1~3, 던져 볼 질문 3, 전환점 1문장)를 보인다. 리포트에는 결론·조언이 없다.
  5. 첫 주장 채점은 첫 답 직후 백그라운드로 미리 돌려 두며 실패하면 이 단계에서 다시 시도한다.
- **예외 처리**
  - 일부만 성공: 성공한 결과는 저장하고, "다시 채점" 버튼으로 빠진 것만 재요청한다. 정리 글이 바뀌면 이전 정리의 점수·리포트는 버린다.
  - 401: E1(정리 글 초안 보관). 그 외 E2~E8.
  - 완료 조건이 "정리를 썼다"가 아니라 "점수 2개와 리포트가 모두 성공"이다. 정리는 썼으나 채점이 실패한 세션은 미완료로 남는다(갭 G8).
  - 리포트 문자열은 400자, 목록은 3개로 절단한다(`clipOutput`).
- **데이터 출처·저장**: `sessions[]`의 `finalSummary`, `scoreBefore`, `scoreAfter`, `report`, `completedAt`. `records`의 `score_before`, `score_after`, `completed_at`. API `score`(kind=`session`, 모델 `claude-haiku-5-5`), `session.report`(Sonnet, effort medium, 2,500토큰).
- **권한**: 회원.
- **상태 유지**: 정리 글은 초안 보관 + 제출 시 `finalSummary`로 저장. 채점 중 이탈해도 부분 결과는 남는다. 정리 화면 자체는 복원하지 않는다.
- **정책**: 채점관은 코치와 분리된 모델·프롬프트이며 사용자가 쓴 글만 평가한다. 총점은 서버가 항목 합으로 계산한다.
- **수용 기준**
  - 사용자는 대화를 마치고 자기 말로 결론을 직접 쓸 수 있다.
  - 사용자는 처음 주장과 마지막 정리의 점수 변화를 세션이 끝나는 순간 볼 수 있다.
  - 사용자는 결론이 아니라 빈틈과 질문으로 구성된 리포트를 받는다.
  - 사용자는 채점이 일부 실패해도 쓴 정리를 다시 쓰지 않고 재시도할 수 있다.
- **코드 경로**: `ThinkingSession.tsx`(submitSummary), `handler.ts`(score, session.report), `prompts.ts`(SCORE_SYSTEM, REPORT_SYSTEM), `logos-ui.tsx`(DeltaRow, RubricBars, ReportBlocks).
- **상태**: 구현됨

- **정책**: 목표 차이 체감 평균 4.0/5 이상(관리자 지표). 응답 의무 없음.

  - 사용자는 설문을 건너뛰어도 결과를 잃지 않는다.
  - 운영자는 설문 평균과 응답 수(n)를 관리자 화면에서 볼 수 있다.
- **코드 경로**: `logos-ui.tsx`(Survey), `ThinkingSession.tsx`, `lib/sync.ts`(surveyVal).
- **상태**: 구현됨

## R3. 오늘의 논증·습관 루프

### R3-F1 오늘의 논증 시작(주제·입장)
- **누가-왜-무엇을**: 매일 10분 습관을 만들려는 로그인 사용자가 오늘의 주제에 입장을 정하고 첫 이유를 쓴다.

- **정상 결과**

  3. 이유를 500자까지 쓴다. 이것이 "처음 주장"이 된다.
  4. 제출하면 R3-F2로 넘어간다.
- **예외 처리**: 입장 선택만으로는 저장하지 않는다. 첫 이유를 보낼 때 기록이 생긴다. 한 날 여러 번 할 수 있다(홈 버튼이 "한 번 더"로 바뀜).
- **데이터 출처·저장**: `topics.ts` + i18n `topics`. 기록은 `sessions[]`(kind=`argue`, `field`, `position`).
- **권한**: 회원.
- **상태 유지**: 입장을 고른 뒤 이탈하면 사라진다. 첫 이유를 보낸 뒤 이탈하면 기록은 남지만 화면은 복원되지 않는다(갭 G1).
- **정책**: 논증 하루 3판, 판당 호출 8회(`QUOTAS.argue`).
- **수용 기준**
  - 사용자는 홈에서 한 번의 탭으로 오늘의 논증을 시작할 수 있다.
  - 사용자는 동의·비동의·조건부 중 입장을 고를 수 있다.
  - 사용자는 오늘 이미 했어도 한 번 더 할 수 있다.
- **코드 경로**: `client/src/pages/Argue.tsx`, `client/src/lib/topics.ts`.
- **상태**: 구현됨

### R3-F2 반문 3라운드
- **누가-왜-무엇을**: 논증 중인 사용자가 AI의 반문 3번을 받으며 자기 근거의 약한 고리를 직접 드러낸다.
- **선행 조건 / 트리거**: R3-F1에서 첫 이유 제출.
- **정상 결과**
  1. 첫 이유 → 반문 1(근거의 구체성), 답 → 반문 2(반례·예외), 답 → 반문 3(전제·가치 충돌) 순서다.
  2. 각 반문 아래에 겨냥한 약점 한 줄(`targetWeakness`)이 보인다.
  3. 반문 3이 나오면 입력창이 "정리하기" 카드로 바뀐다.
- **예외 처리**: E1~E8. 실패 시 "마지막 답 다시 보내기". 3라운드 이후 추가 입력은 무시된다.
- **데이터 출처·저장**: `sessions[].turns[]`(`targetWeakness`). API `argue.turn`(Sonnet, history 최근 8턴).
- **권한**: 회원.
- **상태 유지**: 턴마다 저장되나 화면 복원 없음(갭 G1).
- **정책**: 호출 8회 이내: 반문 3 + 채점 2 + 재시도 3 여유.
- **수용 기준**
  - 사용자는 세 번의 반문으로 근거의 약한 부분을 마주한다.
  - 사용자는 AI가 반대 입장을 주장하지 않고 질문으로만 약점을 드러냄을 본다.
  - 사용자는 실패한 반문을 다시 요청할 수 있다.
- **코드 경로**: `Argue.tsx`(runTurn), `handler.ts`(argue.turn), `prompts.ts`(ARGUE_SYSTEM).
- **상태**: 구현됨

### R3-F3 논증 최종 정리·채점·결과
- **누가-왜-무엇을**: 3라운드를 마친 사용자가 최종 정리를 쓰고 처음 이유와의 점수 차이, 오늘의 연속 기록을 본다.
- **선행 조건 / 트리거**: 반문 3 이후 "정리하기".
- **정상 결과**
  1. 처음 이유를 인용으로 보이고 30~1,500자의 정리를 쓰게 한다.

  3. 둘 다 성공하면 완료로 저장하고 오늘을 활동일로 기록한다.

- **데이터 출처·저장**: `sessions[]`의 `finalSummary`, `scoreBefore`, `scoreAfter`, `completedAt`, `stageReached='통합'`.

- **상태 유지**: 제출한 정리 글은 기록에 저장되나 정리 화면은 복원하지 않는다.
- **정책**: 완주 = 두 점수가 모두 성공한 논증.
- **수용 기준**
  - 사용자는 논증을 끝내면 점수 변화와 오늘 기록이 연속 일수에 반영된 것을 볼 수 있다.
  - 사용자는 채점 실패 시 정리를 다시 쓰지 않고 재시도할 수 있다.
- **코드 경로**: `Argue.tsx`(submitSummary), `handler.ts`(score).
- **상태**: 구현됨

### R3-F4 스트릭·쉬어가기
- **누가-왜-무엇을**: 습관을 이어가는 사용자가 하루 빠져도 기록이 끊기지 않게, 주 1회 쉬어가기를 자동 적용받는다.
- **선행 조건 / 트리거**: 활동 완료 시점(세션 완료, 논증 완료, 아레나 판정, 진단 저장)에 오늘이 활동일로 기록된다. 시작만 한 것은 세지 않는다.
- **정상 결과**
  1. 오늘(없으면 어제)부터 거꾸로 이어진 일수를 센다.
  2. 하루만 빠진 날은, 그 주(월 시작)의 쉬어가기가 남았고 전날이 활동일이면 자동으로 메운다. 쉬어가기로 메운 날은 일수에 세지 않는다.
  3. 홈에 연속 일수, 쉬어가기 남음/사용, 이번 주 월~일 칸(완료·쉬어가기·오늘·미래)을 보인다.
- **예외 처리**: 이틀 이상 빠지면 끊긴다. 오늘이 비어 있는 것은 끊김이 아니다. 기기 간 활동일은 동기화 병합 시 합친다(`mergeRecords`).
- **데이터 출처·저장**: 로컬 `streak{days[], freezesUsed{주키:날짜}}`. 서버에는 따로 저장하지 않고 기록 날짜로 재계산한다.
- **권한**: 비회원(진단만)·회원.
- **상태 유지**: 로컬에 저장된다. 서버 쪽 스트릭 테이블은 없다.
- **정책**: 쉬어가기 주 1회. 날짜는 기기 로컬 날짜 기준이고 서버 KST와 어긋날 수 있다(갭 G9).
- **수용 기준**
  - 사용자는 연속 일수와 이번 주 쉬어가기 남음을 홈에서 볼 수 있다.
  - 사용자가 주 1회 하루를 놓쳐도 연속 기록은 유지된다.
  - 연속 기록은 시작만 한 날이 아니라 완료한 날만 센다.
- **코드 경로**: `client/src/lib/store.ts`(computeStreak, recordActivity), `DashboardHome.tsx`.
- **상태**: 구현됨

### R3-F7 저녁 19시 스트릭 위험 배너
- **누가-왜-무엇을**: 연속 기록이 있는데 오늘 아직 활동이 없는 사용자가 저녁에 기록이 끊길 수 있음을 알아채고 돌아온다.
- **선행 조건 / 트리거**: 기기 로컬 시각 19:00 이후, 오늘이 streak에 기록되지 않음(코칭·논증·아레나 완료를 모두 활동으로 인정), 현재 연속 ≥ 1.
- **정상 결과**
  1. 대시보드 홈 상단에 배너를 보인다. 연속 N일이 오늘 끊길 수 있다는 문장, 자정까지 남은 시간, 이번 주 남은 쉬어가기 수를 함께 표시한다.
  2. 버튼은 둘이다: [10분 논증 시작 → `/dashboard/argue`], [닫기].
  3. 닫으면 그날은 다시 띄우지 않는다.
- **예외 처리**: 활동을 완료하면 즉시 사라진다. 연속 0이면 표시하지 않는다. 푸시·이메일은 보내지 않는다(제외). 수동 "쉬어가기" 버튼은 두지 않는다(쉬어가기는 R3-F4의 자동 적용 그대로).
- **데이터 출처·저장**: 로컬 `streak`에서 계산(`computeStreak`). 닫음 상태는 localStorage에 날짜로 보관한다(키 이름은 코드 대조 전이라 미확인). 노출·클릭은 이벤트 `streak_banner_view`·`streak_banner_click`으로 기록한다(R7-F2).
- **권한**: 회원.
- **상태 유지**: 닫음만 날짜 단위로 유지.
- **정책**: 기준 시각 19:00 고정(사용자 설정 없음). 시간대와 자정까지 남은 시간은 기기 로컬 기준이다.
- **수용 기준**
  - 사용자는 연속 기록이 있고 오늘 활동이 없는 저녁에 배너를 본다.
  - 사용자는 배너에서 한 번의 탭으로 논증을 시작할 수 있다.
  - 사용자는 자정까지 남은 시간과 이번 주 남은 쉬어가기 수를 배너에서 볼 수 있다.
  - 사용자는 배너를 닫으면 그날은 다시 보지 않는다.
- **승인 목업과의 차이(결정됨, 2026-10-13 위임, IA_SCREENS §4.9 M1)**: 목업의 "오늘은 쉬어가기" 수동 버튼은 채택하지 않았다. 자정까지 남은 시간과 남은 쉬어가기 수 표시는 채택했다.
- **코드 경로**: (신규) `DashboardHome.tsx` 또는 `DashboardLayout.tsx`.
- **상태**: 계획(Phase 2)

### R3-F8 첫 실행 온보딩 `/welcome`
- **누가-왜-무엇을**: 처음 로그인한 사용자가 헤매지 않도록, 진단 → 관심 분야 → 첫 오늘의 논증 → 리마인더의 4단계를 안내받는다.
- **선행 조건 / 트리거**: 로그인 직후 `user_meta.onboarded_at`이 null이고 신규 사용자일 때 `/welcome`으로 보낸다. 신규 판정은 진단 수 + 완료 기록 수 = 0이다(결정, 2026-10-13). 기록이 1개 이상이면 리다이렉트하지 않고, 기존 사용자는 `mark_onboarded`로 표시한다.
- **정상 결과**
  1. 1단계 진단(R1-F1) → 2단계 관심 분야(R3-F6, 건너뛸 수 있음) → 3단계 첫 오늘의 논증(R3-F1~F3) → 4단계 리마인더(R3-F5).
  2. 각 단계는 건너뛰기를 제공하며, 마지막에 `mark_onboarded`를 호출하고 `/dashboard`로 이동한다. 우상단 "나중에 하기"(전체 건너뛰기)도 `mark_onboarded`를 호출하고 로컬에 skipped를 남겨, 다른 기기에서도 `/welcome`을 다시 보여 주지 않는다(결정, 2026-10-13).
  3. 4단계의 이름은 "04 캘린더"다(`.ics` 일정이며 푸시 알림이 아니다. 결정, 2026-10-13).
- **예외 처리**: 중간 이탈 시 다음 로그인에서 완료되지 않은 단계부터 이어서 보여 준다(단계 진행도는 localStorage `logos.welcome`, 안). `mark_onboarded` 실패는 조용히 무시하고 다음 방문에 다시 시도한다. 한도(E2)에 걸리면 3단계는 건너뛴다.
- **데이터 출처·저장**: `user_meta.onboarded_at`(RPC `mark_onboarded`로만 쓰기, 본인 select만 허용).
- **권한**: 회원.
- **상태 유지**: 단계 진행도는 로컬. 완료 여부는 서버.
- **정책**: 필수 단계 없음(전부 건너뛰기 가능). 온보딩은 1회만 자동 노출한다.
- **수용 기준**
  - 사용자는 첫 로그인 후 4단계 안내를 따라 첫 진단과 첫 논증까지 마칠 수 있다.
  - 사용자는 어느 단계든 건너뛰고 홈으로 갈 수 있다.
  - 기존 사용자는 온보딩을 강제로 보지 않는다.
- **알려진 빈틈**: 3단계(첫 논증)를 마친 뒤 4단계로 돌아오는 수단이 정해져 있지 않다(G23). 4단계 이름과 전체 건너뛰기 때의 `mark_onboarded` 호출은 결정됐다(IA_SCREENS §4.9 M8·M9). 단계 진입은 이벤트 `onboarding_step`으로 기록한다(R7-F2).
- **코드 경로**: (신규) `client/src/pages/Welcome.tsx`, `App.tsx` 라우트, `lib/auth.tsx`(리다이렉트 판정).
- **상태**: 계획(Phase 2)

### R4-F2 AI 반론 3라운드
- **누가-왜-무엇을**: 토론 중인 사용자가 자기 입장의 반대편을 맡은 AI의 반박 3번에 답한다.
- **선행 조건 / 트리거**: 입장 선택 후 첫 발언 제출.
- **정상 결과**
  1. 사용자 발언 → AI 반박(`arena.turn`, 3~5문장, 사용자 주장 중 하나를 골라 반박, 겨눈 주장 `targetsClaim` 표시) 순서로 3회 반복한다.
  2. 3번째 AI 반박이 끝나면 자동으로 판정(R4-F3)을 호출한다.
- **예외 처리**: 반박 실패는 "다시 시도"(같은 발언 재전송). 판정 실패는 "판정 다시 요청"으로 반박은 다시 부르지 않는다. AI는 출처·통계를 지어내지 않고, 폭력·자해·차별·불법 옹호 논증은 정중히 거절하도록 프롬프트가 지시한다(서버 검증 없음). 그 외 E1~E8.
- **데이터 출처·저장**: 로컬 `arenas[]`(`topicId, side, turns[], result`) → `records`(kind=`arena`). 첫 발언 전에는 저장하지 않는다. API `arena.turn`(history 최근 6턴).
- **권한**: 회원.
- **상태 유지**: 턴마다 저장되나 화면 복원은 없다. 중간에 나가면 기록 화면에 "판정 대기"로 남는다(갭 G1).
- **정책**: 호출 8회 이내: 반박 3 + 판정 1 + 재시도 4 여유.
- **수용 기준**
  - 사용자는 AI의 반박에 3번 답하며 자기 입장을 방어할 수 있다.
  - 사용자는 AI가 어느 주장을 겨눴는지 확인할 수 있다.
  - 사용자는 판정이 실패해도 토론을 다시 하지 않고 판정만 다시 받을 수 있다.
- **코드 경로**: `Arena.tsx`(runTurn, judge), `handler.ts`(arena.turn), `prompts.ts`(ARENA_SYSTEM).
- **상태**: 구현됨

### R4-F3 판정·전적
- **누가-왜-무엇을**: 토론을 마친 사용자가 같은 루브릭의 점수와 승/무/패, 배울 점을 본다.
- **선행 조건 / 트리거**: 3번째 반박 직후 자동 호출, 또는 실패 후 재요청.
- **정상 결과**
  1. 심판(Haiku)이 사용자 발언만 루브릭으로 평가한다. 서버가 총점을 계산하고 70점 이상 승, 40점 이하 패, 그 사이(45~65) 무로 판정한다.
  2. 배울 점 최대 3개와 해당 인용을 보인다. 인용이 토론 원문에 없으면 서버가 비운다.

  3. "다음 목표"는 가장 가까운 미도달 항목과 힌트 한 줄로 보인다. 힌트는 루브릭 설명형 문구이며 내용에 대한 조언이 아니다.
- **예외 처리**: 점수 해상도가 5점 단위라 같은 단계가 반복될 수 있다. 달성 판정은 기록에서 재계산하므로 기록 삭제 시 함께 사라진다. 미도달 항목이 없으면 "다음 목표"를 보이지 않는다(안).
- **데이터 출처·저장**: `scoreAfter`·아레나·진단 점수에서 계산. 달성일은 해당 기록 날짜. NEW를 이미 봤는지는 로컬에 둔다(저장 위치는 코드 대조 전이라 미확인).
- **권한**: 회원.
- **상태 유지**: 계산 값. NEW 확인 여부만 유지.
- **정책**: 임계값은 루브릭 단계(L2·L3) 그대로이며 별도 수치는 없다.
- **수용 기준**
  - 사용자는 항목별로 L2·L3에 처음 도달한 날짜와 기록을 볼 수 있다.
  - 사용자는 세션을 마친 직후 새 마일스톤을 한 줄 안내로 받는다.
  - 사용자는 가장 가까운 다음 목표 한 가지를 볼 수 있다.
- **승인 목업과의 차이(결정됨, 2026-10-13 위임, IA_SCREENS §4.9 M3)**: 목업의 L2·L3 라벨과 "다음 목표" 힌트를 채택했다. 초안의 "중간 단계 3회 연속"은 뺐다.
- **코드 경로**: (신규) `lib/store.ts`(마일스톤 계산), `ThinkingSession.tsx`·`Argue.tsx` 완료 화면, `Analytics.tsx`.
- **상태**: 계획(Phase 2)

### R5-F8 세션 리포트 "작성 비율"
- **누가-왜-무엇을**: "AI가 대신 생각해 준 것 아닌가"를 의심하는 사용자와 심사자에게, 결론을 사용자가 직접 썼음을 리포트에서 보여 준다. 일반 AI 대화와의 차이를 구조로 드러내는 장치다.
- **선행 조건 / 트리거**: 코칭 리포트 화면과 오늘의 논증 결과 화면에서 `finalSummary`가 있을 때. 아레나에는 표시하지 않는다.
- **정상 결과**
  1. 카드는 `finalSummary`가 있으면 항상 표시한다(초안의 "중복 0일 때만" 규칙은 폐기, 결정 2026-10-13).
  2. 3칸: [코치가 던진 질문 N: 물음표를 포함한 코치 발화 수, 첫 고정 질문은 제외] [직접 쓴 글자 N자] [코치 말과 겹친 표현 X%: 어절 4-gram 기준].
  3. 겹침이 0%이고 정리가 4어절 이상이면 "모두 당신이 썼어요"를 보이고, 그 밖에는 "X%가 코치의 표현과 겹쳐요"를 보인다.
  4. 설명 문장은 단정하지 않고 "보통의 AI 대화라면 답이나 목록을 먼저 받는 경우가 많아요."로 쓴다.
- **예외 처리**: 코치 턴이 없거나 정리가 없으면 카드 없음. "코치가 준 답" 칸은 두지 않는다(물음표 휴리스틱이 답과 질문을 잘못 가를 위험, 결정 2026-10-13). 질문 수는 물음표 휴리스틱이라 질문이 아닌 문장이나 물음표 없는 질문을 틀리게 셀 수 있다(갭 G13). "답 0개"는 프롬프트 규칙이며 코드로 검증하지 않는다.
- **데이터 출처·저장**: `turns[]`와 `finalSummary`로 클라이언트에서 계산한다. 저장하지 않는다(안).
- **권한**: 회원.
- **상태 유지**: 계산 값.
- **정책**: 어절 4-gram(공백 정규화 후)으로 확정(결정, 2026-10-13). 한국어 어절 특성상 겹침이 거의 0%로 나오는지는 파일럿 데이터로 점검한다.
- **수용 기준**
  - 사용자는 결론을 직접 썼다는 근거(질문 수, 직접 쓴 글자 수, 겹침 비율)를 리포트에서 볼 수 있다.
  - 사용자는 코치 문장을 그대로 베낀 정리에서는 "모두 당신이 썼어요"를 보지 않고 겹침 비율을 본다.
- **승인 목업과의 차이(결정됨, 2026-10-13 위임, IA_SCREENS §4.9 M4)**: 목업의 3칸 카드를 채택하되 두 번째 칸을 "코치가 준 답"에서 "직접 쓴 글자 N자"로 바꿨다. 목업의 반사실 문장("보통의 AI 대화였다면 …받았을 거예요")은 단정이라 위 설명 문장으로 대체했다.
- **코드 경로**: (신규) `lib/store.ts` 또는 `lib/ngram.ts`, `ThinkingSession.tsx`(완료 화면), `Argue.tsx`(결과 화면), `logos-ui.tsx`.
- **상태**: 계획(Phase 2)

## R6. 계정·데이터

### R6-F1 로그인·보호 라우트·로그아웃
- **누가-왜-무엇을**: 기록을 저장하고 기기 간에 쓰려는 사용자가 Google 계정으로 로그인한다. 이메일 가입은 없다.
- **선행 조건 / 트리거**: 로그인 버튼(`/login`), 또는 보호 라우트 접근(`RequireAuth`가 `/login?next=`로 보냄), 또는 401(E1).
- **정상 결과**
  1. `/login`에서 Google 버튼 → Supabase OAuth(PKCE) → `/auth/callback?next=` 도착.
  2. 세션이 잡히면 `next`(같은 사이트 절대 경로만 허용, 기본 `/dashboard`)로 이동한다.
  3. 로그인 직후 `onSignIn`(R6-F3)과 관리자 여부(`is_admin` RPC)를 확인한다.
  4. 로그아웃은 미전송 기록을 3초 안에 올려 보고, 못 올린 것이 있으면 확인창을 띄운 뒤 로컬 캐시·초안을 비우고 로그아웃한다.
- **예외 처리**
  - Supabase env 없음: "로그인 준비 중" 안내, 버튼 비활성.
  - OAuth 시작 실패: "로그인에 실패했어요". 콜백의 `error_description`은 화면에 싣지 않고 일반 문구를 쓴다. 15초 안에 세션이 안 잡히면 오류와 재시도 링크.
  - `next`에 `//`·역슬래시가 있으면 기본값으로 대체(오픈 리다이렉트 방지).
  - 로그아웃 확인에서 취소하면 로그아웃하지 않는다.
- **데이터 출처·저장**: Supabase Auth 세션(브라우저 저장). 이름·프로필 이미지는 Google 메타데이터에서 표시만 한다. 공개 라우트: `/`, `/about`, `/features`, `/pricing`, `/privacy`, `/login`, `/auth/callback`, `/dashboard/diagnostic`, `/404`. 나머지는 로그인 필요.
- **권한**: 비회원이 시작, 회원이 사용.
- **상태 유지**: 세션 토큰은 자동 갱신된다. 로그인 전 쓰던 글은 초안으로 복원된다.
- **정책**: Google 로그인만 제공. 만 18세 미만 이용 불가를 처리방침·이용약관에 명시했고, 로그인 화면의 동의 체크박스(`auth.consent`, "만 18세 이상이며 …")로 확인한다(갭 G14).
- **수용 기준**
  - 사용자는 Google 계정 한 번으로 로그인하고 가려던 화면으로 돌아간다.
  - 사용자는 로그인 실패 시 이유를 알고 다시 시도할 수 있다.
  - 사용자는 로그아웃할 때 아직 올리지 못한 기록이 있으면 경고를 받는다.
- **코드 경로**: `client/src/lib/auth.tsx`, `pages/Login.tsx`, `pages/AuthCallback.tsx`, `components/RequireAuth.tsx`, `lib/supabase.ts`.
- **상태**: 구현됨

### R6-F2 로컬 우선 저장·서버 동기화
- **누가-왜-무엇을**: 회원이 기록을 잃지 않고 여러 기기에서 쓰도록, 기록은 먼저 로컬에 저장하고 뒤에서 서버에 올린다.
- **선행 조건 / 트리거**: 기록이 만들어지거나 바뀔 때(`upsertSession`·`upsertArena`·`addDiagnostic`) 회원이면 outbox에 올린다. 로그인 시 서버 기록을 받아 병합한다.
- **정상 결과**
  1. 변경 후 1초 디바운스로 `records`에 upsert한다(20건 묶음).
  2. 실패하면 outbox를 유지하고 2초부터 최대 60초까지 백오프로 재시도한다. `online` 이벤트와 탭이 숨겨질 때도 시도한다.
  3. 로그인 시 서버 기록을 1,000행씩 받아 id 기준으로 병합한다. outbox에 있는 로컬 변경만 로컬이 이기고 나머지는 서버가 이긴다.
  4. 사용자 메뉴에 "미동기화 N건"을 표시한다.
- **예외 처리**
  - 묶음이 실패하면 한 행씩 다시 보내 한 행이 전체를 막지 않게 한다.
  - 서버가 제약 위반(Postgres 22xxx·23xxx; 행 수 2,000 초과, 256KB 초과 포함)으로 거부하면 outbox에서 버린다. 콘솔 경고만 남기고 사용자에게 알리지 않는다(갭 G15).
  - 전송 중 같은 기록이 또 바뀌면 outbox에 남겨 다시 보낸다(탭 간 변경도 내용 비교로 감지).
  - 로컬 저장소 접근 불가: 메모리 폴백으로 동작하며 새로고침 시 사라진다. 손상된 `logos.v1`은 `.bak`으로 백업 후 새로 만든다.
  - 비회원은 서버로 보내지 않는다.
- **데이터 출처·저장**: `records(id, user_id, kind, started_at, completed_at, score_before, score_after, survey_diff, survey_self, verdict, prompt_version, data)`. RLS: 본인 행만 select/insert/update/delete.
- **권한**: 회원.
- **상태 유지**: outbox는 id·종류만 localStorage에 둔다. 탭을 닫아도 다음 방문에 이어서 보낸다.
- **정책**: 사용자당 `records` 2,000행(트리거 `enforce_record_limit`), 행당 `data` 256KB 미만. 충돌 해결은 "outbox 우선, 나머지 서버 우선"이며 같은 기록을 두 기기에서 동시에 고치면 마지막 업로드가 이긴다.
- **수용 기준**
  - 사용자는 오프라인이어도 기록을 쓰고 연결이 돌아오면 자동으로 올라간다.
  - 사용자는 다른 기기에서 로그인하면 이전 기록을 볼 수 있다.
  - 사용자는 아직 올라가지 않은 기록 수를 볼 수 있다.
  - 사용자는 다른 사람의 기록에 접근할 수 없다.
- **코드 경로**: `client/src/lib/store.ts`, `client/src/lib/sync.ts`, `supabase/migrations/20261013000100_records.sql`, `…0400_quota_carryover.sql`(행 수 상한).
- **상태**: 구현됨

### R6-F3 비회원 기록 이전·계정 전환
- **누가-왜-무엇을**: 비회원일 때 진단을 한 사용자가 로그인해도 기록이 사라지지 않게 하고, 공용 기기에서 다른 계정 기록이 섞이지 않게 한다.
- **선행 조건 / 트리거**: 로그인 직후(`onSignIn`).
- **정상 결과**
  1. 캐시의 소유자가 없으면(비회원 기록) 전부 outbox에 올려 이 계정으로 업로드하고 "{n}개 기록을 계정에 저장했어요" 토스트(`i18n/ko/auth.ts` `migrated`)를 보인다.
  2. 이후 `flush` → `pullAll`로 서버 기록과 병합한다.
- **예외 처리**: 캐시 소유자가 다른 계정이면 캐시·outbox·초안을 모두 버리고 새 계정으로 시작한다(되돌릴 수 없음; 이전 계정의 미동기화 기록은 사라질 수 있다, 갭 G15). 병합 중 로그아웃·계정 전환이 일어나면 낡은 결과를 적용하지 않는다(generation 비교).
- **데이터 출처·저장**: `logos.v1.ownerId`.
- **권한**: 회원.
- **상태 유지**: 해당 없음.
- **정책**: 이전은 로그인 시 한 번 일괄이다.
- **수용 기준**
  - 사용자가 로그인 전에 한 진단은 로그인 후에도 남아 있다.
  - 사용자는 이전된 건수를 안내받는다.
  - 사용자는 다른 사람이 쓰던 기기에서 로그인해도 그 사람의 기록을 보지 않는다.
- **코드 경로**: `lib/sync.ts`(onSignIn, mergeRecords), `lib/auth.tsx`.
- **상태**: 구현됨

### R6-F4 데이터 내보내기(JSON)
- **누가-왜-무엇을**: 자기 기록을 가져가려는 사용자가 JSON 파일로 내려받는다.
- **선행 조건 / 트리거**: 설정 > 내보내기, 또는 홈의 내보내기 버튼.
- **정상 결과**
  1. 설정에서는 미전송 기록을 올리고 서버 기록을 받아 병합한 뒤 파일을 만든다.
  2. `logos-export-YYYY-MM-DD.json`에 설명 문구, 내보낸 시각, participantId, 지표(완주율·평균 Δ·스트릭·재방문), 세션·진단·아레나·스트릭 전체가 들어간다.
- **예외 처리**: 서버 병합이 실패하면 로컬 내용만 내보내고 토스트로 알린다. 홈의 내보내기는 서버 병합 없이 로컬만 낸다.
- **데이터 출처·저장**: 로컬 캐시(`buildExport`). 관심 분야·언어·테마·사전 신청은 포함하지 않는다.
- **권한**: 회원.
- **상태 유지**: 해당 없음.
- **정책**: 형식은 JSON 한 가지(CSV 없음).
- **수용 기준**
  - 사용자는 자신의 모든 기록을 파일로 내려받을 수 있다.
  - 사용자는 내보내기가 서버 최신본인지 로컬만인지 안내받는다.
- **코드 경로**: `pages/Settings.tsx`(exportData), `lib/store.ts`(buildExport), `DashboardHome.tsx`.
- **상태**: 구현됨

### R6-F5 기록 삭제·계정 삭제
- **누가-왜-무엇을**: 자기 데이터를 지우려는 사용자가 설정에서 기록만, 또는 계정 전체를 삭제한다.
- **선행 조건 / 트리거**: 설정 > 기록 모두 삭제 / 계정 삭제.
- **정상 결과**
  1. 기록 삭제: 확인창 후 `delete_my_data` RPC로 `records`·`waitlist`를 지우고 로컬 캐시를 비운다(계정과 로그인은 유지). **계획(Phase 2, 2026-10-13 결정)**: 같은 RPC가 `events`(해당 `user_id`)와 `user_meta`도 지운다. `user_meta`에는 파일럿 군 배정(`cohort_code`, `arm`)·동의 기록·UTM first-touch가 들어 있어 함께 사라진다. 이 사용자가 같은 코드로 다시 참가하면 다른 군이 될 수 있다(R7-F6 위험, 갭 G25).
  2. 계정 삭제: 확인 단어를 직접 입력해야 버튼이 켜진다. `delete_my_account` RPC가 `auth.users`를 지우고(관련 행 cascade), 로컬을 비우고 로그아웃한 뒤 `/`로 이동한다.
  3. 삭제 전에 outbox를 비워 삭제 뒤 되살아나지 않게 한다.

### R7-F2 퍼널 이벤트 계측
- **누가-왜-무엇을**: 운영자가 어디서 사람들이 빠지는지 알도록 1st-party 이벤트를 수집한다. 외부 분석 SaaS는 쓰지 않는다.
- **선행 조건 / 트리거**: 주요 화면 진입·행동 시 클라이언트가 이벤트를 큐에 쌓아 묶음으로 전송한다.
- **정상 결과**
  1. 이벤트: `events(anon_id, user_id, name, props, path, client_ts)`. `anon_id`는 브라우저에서 만든 랜덤 uuid(localStorage), 로그인하면 `user_id`가 함께 붙는다.
  2. `name`은 서버가 거부하는 화이트리스트다. 이름은 다음과 같다(`shared/events.ts` 대조). 퍼널(`admin_funnel`의 단계): `landing_view` → `diagnostic_start` → `diagnostic_done` → `signup` → `session_start` → `session_complete`. 그 밖: `join_view`, `app_open`(하루 1회), `session_open`(코칭 화면 진입), `session_summary`, `argue_start`·`argue_complete`, `arena_start`·`arena_complete`, `onboarding_step`, `recap_view`, `milestone_seen`, `streak_banner_view`·`streak_banner_click`, `reminder_ics`. 초안에 있던 `cta_click`, `login_start`·`login_done`, `quota_hit`, `error_shown`, `survey_submit`, `session_stage` 등은 구현 목록에 없다. 목록 밖 이름은 서버가 거부한다.
  3. `props`는 숫자·불리언·열거형만 허용하고 직렬화 512바이트 이하다. 문자열 값은 32자 이하만 받는다(2026-10-13 결정). 자유 텍스트·IP·이메일·글 내용은 저장하지 않는다.
  4. 전송은 RPC `track(events jsonb)`(security definer, anon 호출 허용)로 한다. 호출당 25건, `anon_id`별 분당 30건·24시간 300건, 전역 분당 600건·24시간 20,000건을 넘으면 거부한다. 상한 검사는 advisory lock으로 직렬화한다. 공개 쓰기 엔드포인트라 IP 단위 제한 없이는 남용을 완전히 막을 수 없고, 상한은 증가 폭만 제한한다(잔여 위험).
  5. 비회원 진단 시작·제출·결과도 같은 방식으로 기록한다(R7-F2-D1).
- **예외 처리**: 전송 실패는 사용자에게 보이지 않고 큐에 남겨 다음 주기에 다시 보낸다(수집은 best-effort, 기능을 막지 않는다). 한도 초과 시 서버가 초과분을 버린다. GPC 신호(`navigator.globalPrivacyControl`) 또는 DNT가 켜져 있으면 전송하지 않는다("존중"으로 결정, 2026-10-13 사용자 위임). 큐는 메모리와 localStorage(`logos.evq`, 최대 50건)에 둔다.
- **데이터 출처·저장**: `public.events`(RLS로 일반 select 불가, 쓰기는 `track`만). 읽기는 관리자 RPC로만.
- **권한**: 비회원·회원이 쓰기(RPC), 관리자만 읽기.
- **상태 유지**: `anon_id`(`logos.aid`)와 큐를 localStorage에 둔다. 로그아웃·기록 삭제·계정 삭제 때 `anon_id`를 새로 만들고 큐·first-touch를 지운다(다른 사용자에게 귀속 방지).
- **정책**: 화이트리스트·props 규칙·rate limit은 위와 같다. 보관 180일(R7-F5, 기본값으로 결정). 처리방침에 항목·목적·보관기간·GPC/DNT 존중을 추가한 뒤 배포한다(갭 G14). 사용자가 기록 삭제·계정 삭제를 하면 그 `user_id`의 이벤트도 지운다(R6-F5). 로그인 전 `anon_id` 이벤트 중 아직 연결되지 않은 것도 현재 기기의 `anon_id`를 함께 넘겨 지운다(`delete_my_data(p_anon)`). 다른 기기의 미연결 이벤트는 180일 파기에 맡긴다(G26).
- **수용 기준**
  - 운영자는 방문부터 세션 완료까지 단계별 도달 수를 얻을 수 있다.
  - 사용자의 글·이메일·IP는 이벤트에 저장되지 않는다.
  - 사용자가 GPC를 켜면 이벤트가 전송되지 않는다.
  - 이벤트 수집이 실패해도 사용자 기능은 영향을 받지 않는다.
- **코드 경로**: (신규) `client/src/lib/track.ts`, `supabase/migrations/*_events.sql`, 각 페이지의 호출부.
- **상태**: 계획(Phase 2)
- **R7-F2-D1 비회원 진단 이벤트**: 비회원은 `anon_id`만 갖는다. `diagnostic_start`와 `diagnostic_done`을 보낸다(props는 구현 대조 전이라 미확인. 초안은 문항 id, 총점 구간). 로그인하면 같은 `anon_id`의 이벤트와 `user_id`를 연결(`claim_profile`, R8-F4)한다. 비회원 진단 점수 자체는 서버 검증하지 않는다(기본값으로 결정, 2026-10-13).

### R7-F3 관리자 퍼널·이탈 단계·방문 D1/D7
- **누가-왜-무엇을**: 운영자가 단계별 전환율, 세션 이탈 단계 분포, 방문 기준 재방문율을 본다.
- **선행 조건 / 트리거**: `/admin`에 R7-F2 데이터가 있을 때.
- **정상 결과**
  1. `admin_funnel(from, to)`: 방문 → 진단 시작 → 진단 완료 → 가입(로그인) → 첫 세션 시작 → 첫 세션 완주(→ D7)의 단계별 `anon_id`·사용자 수와 전환율. (초안은 "방문 → 로그인 → 첫 진단/첫 세션 → 첫 답 → 완주"로 적었으나 PRD §6.3과 맞췄다. 실제 구현 단계는 미확인.)
  2. `admin_abandon(from, to)`: 시작했으나 완료하지 못한 코칭 세션의 마지막 도달 단계(표면/도전/핵심/통합/정리 화면) 분포.
  3. 방문 기준 D1/D7: 첫 방문일 기준 N일째 방문(이벤트 있는 날) 비율. 확정 KPI인 "세션 시작 기준 D7"과 나란히 놓고 보조 지표로 표시한다.
  4. 확정 KPI 두 개를 기록 기반으로 함께 돌려준다(2026-10-13 결정).
     - `north_star`: 코칭 세션(`kind='session'`) 중 `finalSummary`를 쓴 비율. `completed_at` 유무와 무관하다(채점·리포트 실패와 분리). 분모는 사용자 답이 1회 이상 있어 저장된 코칭 세션이다(R2-F1).
     - `d7_session`: 사용자별 첫 session/argue 시작일(KST)을 기준으로 +7일째 날에 session/argue를 시작한 사용자 비율. 이벤트가 아니라 `records.started_at`으로 센다. 첫 시작 후 7일이 아직 지나지 않은 사용자는 분모에서 뺀다(안).
- **예외 처리**: 기간 내 이벤트가 없으면 "—". 관리자 본인의 이벤트는 제외한다. `anon_id`와 `user_id` 연결 전 이벤트는 같은 사람으로 합치지 못한다(연결은 `claim_profile` 시점 이후만).
- **데이터 출처·저장**: `events`, `records`, `user_meta`. RPC는 모두 `is_admin()` 재검사.
- **권한**: 관리자.
- **상태 유지**: 해당 없음.
- **정책**: KPI 1차 = 세션 완주율(시작한 세션 중 마지막 정리를 직접 쓴 비율) 60% = `north_star`, D7 = 첫 세션 후 7일째 세션을 시작한 비율 40% = `d7_session`. 방문 기반 D7은 보조. 관리자 화면의 두 KPI는 확정 정의로 계측하고, 홈 화면 완주율은 기존 정의(`completedAt`)의 참고 값이다(갭 G8·G9). 퍼널 단계 표기는 PRD §6.3(방문 → 진단 시작 → 진단 완료 → 가입 → 첫 세션 시작 → 첫 세션 완주 → D7)을 따른다(위 1번의 간략 표기와 같은 단계).
- **수용 기준**
  - 운영자는 어느 단계에서 가장 많이 이탈하는지 볼 수 있다.
  - 운영자는 방문 기준과 세션 시작 기준 D7을 구분해 볼 수 있다.
- **코드 경로**: (신규) `Admin.tsx` 섹션, `supabase/migrations/*_admin_funnel.sql`.
- **상태**: 계획(Phase 2)

### R7-F4 관리자 유입원 집계
- **누가-왜-무엇을**: 운영자가 어떤 유입원(UTM·referrer)에서 온 사람이 가입·첫 세션·완주까지 가는지 비교한다.
- **선행 조건 / 트리거**: R8-F4의 first-touch가 `user_meta`에 쌓였을 때.
- **정상 결과**: `admin_acquisition(from, to)`가 유입원(`utm_source`/`utm_medium`/`utm_campaign` 또는 `ref_host`, 없으면 "direct")별 가입자 수, 첫 세션 시작률, 완주율, D7을 돌려준다.
- **예외 처리**: first-touch가 없는 사용자는 "unknown". 표본이 작은 행(n < 5, 안)은 숫자 대신 "n<5"로 표시한다.
- **데이터 출처·저장**: `user_meta`(first-touch), `records`, `events`.
- **권한**: 관리자.
- **상태 유지**: 해당 없음.
- **정책**: first-touch는 한 번 쓰면 바꾸지 않는다(마지막 클릭 모델 아님).

### R7-F5 이벤트 보관·파기

- **예외 처리**: 관리자가 아니면 거부. 한 번에 지우는 양에 상한을 둔다(안, 타임아웃 방지).

### R7-F6 파일럿 참여 `/join` (군 배정·동의·철회)
- **누가-왜-무엇을**: 파일럿 참가자가 안내 링크(`/join?c=코드`)로 들어와 동의하고 A/B 군에 고정 배정된다.
- **선행 조건 / 트리거**: `/join?c=<코드>` 접근. 코드는 `private.cohorts`에 있는 유효한 값이어야 하고 8자 이상이다(짧은 코드는 추측으로 찾을 수 있어 막음).
- **정상 결과**
  1. 공개 페이지에서 연구 목적, 수집 항목(글·점수·설문), 블라인드 채점에 쓰임, 보관, 철회 방법을 안내하고 동의 체크를 받는다. 동의 문구에는 버전이 있다. 체크박스는 기본 해제다. 문구는 기간 "4~8주", "일주일에 세 번 이상, 10분 정도"(권장), "원하면 끝나고 짧은 인터뷰"(선택), "코칭 대화 내용은 연구 분석에 쓰지 않아요(채점에는 진단 글만 써요)"를 쓴다(결정, 2026-10-13). 근거: `admin_rater_export`는 진단 글만 내보내고 `admin_export`는 본문을 뺀다. 동의 체크 상태는 로그인(OAuth) 왕복 동안 sessionStorage에 보관하고 로그인 후 같은 탭에서 복원한다.
  2. 로그인 후 RPC `join_cohort(code, consent_version)`이 `user_meta`에 `cohort_code`, `arm`(A 또는 B), `consent_version`, `consent_at`을 기록한다. 배정은 코드별 균형(안: 가입 순서 교대 또는 해시)으로 하고 한 번 정해지면 바뀌지 않는다. 참가자는 자기 군을 볼 수 없다: `user_meta`의 `arm` 열은 본인 select 권한에서 빠져 있고 `join_cohort`도 군을 돌려주지 않는다(블라인딩).
  3. 이후 진단·코칭 화면은 군과 무관하게 동일하게 동작한다(B군도 코칭을 차단하지 않고 사용을 오염으로 집계하는 것으로 결정, 2026-10-13 사용자 위임).
  4. 설정에 "파일럿 참여 중 · 동의 버전·일시" 영역과 "동의 철회" 버튼을 둔다. `withdraw_consent()`가 `consent_withdrawn_at`을 기록하고 이후 분석·export에서 제외한다(안).
- **예외 처리**: 유효하지 않은/만료된 코드는 안내 후 일반 가입으로 보낸다. 이미 배정된 사용자가 다른 코드로 들어오면 기존 배정을 유지하고, 코드가 유효한지와 관계없이 "이미 참가 중"만 알린다(코드 유효 여부를 드러내지 않음). 동의하지 않으면 배정하지 않는다. 철회 후 같은 코드로 다시 참가하면 동의만 복원하고 군 배정은 그대로 둔다(2026-10-13 결정, 구현 `join_cohort`). 이미 export된 CSV 파일은 회수할 수 없다는 점을 동의 문구에 적는다. **위험**: 기록 삭제(R6-F5)가 `user_meta`를 지우면 군 배정과 동의 기록도 사라진다. 같은 코드로 다시 참가하면 다른 군에 배정될 수 있어 "배정 고정" 원칙이 깨진다(G25).
- **데이터 출처·저장**: `user_meta`(cohort_code, arm, consent_version, consent_at, 본인 select만 허용하되 `arm` 열 제외, 쓰기는 RPC만), `private.cohorts`(코드, 이름, 시작·종료, 군 배분 규칙).
- **권한**: 회원(동의는 로그인 후).
- **상태 유지**: 서버에 고정(단, 사용자가 기록 삭제를 하면 함께 지워짐, G25). 동의 화면 진행은 저장하지 않는다.
- **정책**: 파일럿 규모 n=40~60, 4~8주(`FEEDBACK_PLAN.md` §4). 철회 시 데이터를 삭제할지 분석에서만 제외할지는 미정이다(기본안: 분석·export 제외, 원본 삭제는 R6-F5로 요청). 동의 문구 법률 검토는 미확인.
- **수용 기준**
  - 참가자는 안내 링크로 들어와 동의 내용을 읽고 동의해야만 배정된다.
  - 참가자는 설정에서 언제든 동의를 철회할 수 있다.
  - 운영자는 참가자가 어느 군인지 바꿀 수 없다(배정 고정).
  - 참가자에게 자기 군(A/B)은 앱 화면과 API 응답 어디에도 드러나지 않는다(`arm` 열 select 제외). 동의 화면은 승인 목업대로 "두 그룹 중 하나에 배정돼요. 그룹에 따라 LOGOS 또는 다른 AI 도구로 연습해요"라고 적어 그룹 존재와 역할을 알린다(설명 동의에 필요해 유지로 결정, 2026-10-13 사용자 위임, IA_SCREENS §4.9 M6).
- **빈틈**: 파일럿 종료·사후 진단 시점 안내, 군별 이용 안내(A: LOGOS, B: 일반 챗봇)의 전달 수단, 가입 전에 이미 진단한 참가자의 사전 기준 처리는 정해지지 않았다(G24). 동의 상태 보관(OAuth 왕복)은 sessionStorage로 결정됐다(G24 ④).
- **코드 경로**: (신규) `client/src/pages/Join.tsx`, `Settings.tsx`, `supabase/migrations/*_cohorts.sql`.
- **상태**: 계획(Phase 2)

### R7-F7 블라인드 채점 export
- **누가-왜-무엇을**: 운영자가 사람 채점자 2명에게 줄 글을, 누가 쓴 글인지(군·사전/사후) 가린 채 내보내 AI 채점과의 일치도를 본다.
- **선행 조건 / 트리거**: 관리자 화면의 "블라인드 채점 CSV" 버튼. 대상은 동의하고 철회하지 않은 참가자의 진단 답안(사전·사후).
- **정상 결과**
  1. `admin_rater_export`가 `blind_id`, `form`, `text` 3열만 담은 CSV를 순서를 섞어 돌려준다. `blind_id`는 글마다 새로 만든 난수이고, `form`은 진단 문항 식별자다(사전/사후, 군, 사용자 정보 없음).
  2. 별도 RPC `admin_rater_key`가 `blind_id` ↔ (기록 id, 시점, 군)을 돌려준다. 채점이 끝난 뒤에만 쓰도록 UI에서 분리된 버튼으로 둔다.
  3. 대응표는 `private.rater_keys`에 저장해 재내보내기 때 같은 `blind_id`를 쓴다.
  4. 대상은 동의한 참가자가 처음 참가한 시각(`user_meta.joined_at`, 재참가·철회로 바뀌지 않음) 이후에 시작한 진단만이다. 시점(사전/사후)도 이 집합 안의 순서로 정한다. 참가 전에 쓴 진단(비회원 진단 후 로그인 등)은 동의 범위 밖이라 내보내지 않는다(2026-10-13 결정). 파일럿 문항 교차 배정도 참가 이후 진단만 기준으로 센다.
- **예외 처리**: 텍스트에 이름·이메일 같은 식별 정보가 들어 있을 수 있다. 자동 제거하지 않는다(갭 G16). 사전/사후 쌍이 모두 없는 참가자는 포함 여부를 선택하게 한다(안). 철회한 참가자는 제외한다.
- **데이터 출처·저장**: `records.data`(진단 답안), `user_meta`, `private.rater_keys`.
- **권한**: 관리자.
- **상태 유지**: 대응표 영구 저장.
- **정책**: CSV는 수식 주입 방어와 BOM을 적용한다(기존 `csv.ts`). 파일 취급 기준(저장 위치·삭제)은 정해지지 않았다.
- **수용 기준**
  - 채점자는 군·시점·사용자 정보 없이 글과 문항 식별자만 받는다.
  - 운영자는 채점 후 별도 대응표로 결과를 원래 기록에 연결할 수 있다.
  - 운영자는 순서가 섞인 목록을 받아 순서로 시점을 추측할 수 없다.
- **코드 경로**: (신규) `Admin.tsx`, `supabase/migrations/*_rater.sql`, `lib/csv.ts`.
- **상태**: 계획(Phase 2)

### R8-F4 UTM·referrer first-touch
- **누가-왜-무엇을**: 운영자가 어디서 온 방문자가 가입·완주까지 가는지 알도록, 첫 방문의 UTM과 referrer host를 기억했다가 가입 후 계정에 붙인다.
- **선행 조건 / 트리거**: 첫 방문 URL의 `utm_source`·`utm_medium`·`utm_campaign` 또는 `document.referrer`.
- **정상 결과**
  1. 첫 방문 시 localStorage(`logos.ft`)에 UTM 3종과 `ref_host`(호스트명만, 경로·쿼리 제외)를 한 번만 저장한다. 이미 있으면 덮어쓰지 않는다.
  2. 로그인 직후 RPC `claim_profile(first_touch)`가 `user_meta`에 값이 비어 있을 때만 기록한다(first-touch 유지).
  3. 같은 시점에 `anon_id`와 `user_id`를 연결한다(R7-F2).
- **예외 처리**: UTM 값은 길이(예: 64자)와 문자 집합을 제한해 저장한다(안). referrer가 같은 사이트면 기록하지 않는다. GPC/DNT가 켜져 있으면 저장하지 않는다("존중"으로 결정, 2026-10-13). 저장소를 못 쓰면 기록 없이 진행한다.
- **데이터 출처·저장**: localStorage `logos.ft` → `user_meta`(utm_source, utm_medium, utm_campaign, ref_host).
- **권한**: 비회원이 수집, 회원 계정에 귀속. 본인 select만.
- **상태 유지**: 첫 방문 값을 로그인 때까지 유지.
- **정책**: first-touch만 쓴다. 광고 식별자·IP·전체 URL은 저장하지 않는다.
- **수용 기준**
  - 운영자는 가입자별 첫 유입원을 확인할 수 있다.
  - 사용자는 이후 방문에서 다른 UTM으로 들어와도 첫 유입원이 바뀌지 않는다.
- **코드 경로**: (신규) `client/src/lib/attribution.ts`, `lib/auth.tsx`(claim_profile 호출), `supabase/migrations/*_user_meta.sql`.
- **상태**: 계획(Phase 2)

## R9. 비기능 요구사항

### R9-F1 이용 한도·비용 통제
- **누가-왜-무엇을**: 운영자가 무료 운영 중 API 비용이 통제 불능이 되지 않도록 사용자별·sid별 한도를 서버에서 강제한다.
- **선행 조건 / 트리거**: 모든 `/api/coach` 호출(비회원 진단 제외)에서 LLM 호출 전에 `consume_quota`를 부른다.
- **정상 결과**
  1. 사용자 JWT로 RPC를 호출해 서명·만료 검증과 한도 확인·기록을 한 번에 한다(서버에 JWT 시크릿·서비스 키가 필요 없다). 사용자별 advisory lock으로 직렬화한다.
  2. 통과하면 `usage_events`에 (user, kind, ref=sid, action)을 추가하고 LLM을 호출한다.
- **예외 처리**: 한도 초과는 429 `quota`(`reason` day·refs·ref_calls, E2). 한도 RPC가 5초 안에 응답하지 않거나 장애면 503(E5, 요청 거부). 삭제 계정 FK 위반은 401. 한도 소진 후 AI 호출이 실패해도 차감은 되돌리지 않는다(갭 G2).
- **데이터 출처·저장**: `usage_events`(추가만 가능, 사용자 select는 본인 행만, 생성 시각은 서버 시각 ±1분만 허용), `private.deleted_usage`.
- **권한**: 회원(서버 강제). 비회원은 진단 채점만 허용하고 IP 한도를 쓴다(R9-F2).
- **상태 유지**: 서버 원장.
- **정책** (`shared/quotas.ts`의 실제 값)

  | 종류 | 하루 판 수 | 판당 호출 수 |
  |---|---|---|
  | 코칭 세션 (`session`) | 2 | 32 |
  | 오늘의 논증 (`argue`) | 3 | 8 |
  | 아레나 (`arena`) | 3 | 8 |
  | 진단 (`diagnostic`) | 2 | 2 |
  | 회원 1인 하루 전체 호출 상한 | 100 | |
  | 비회원 진단 (IP당 하루) | 3 | |

  - 하루는 KST 자정. 코칭 중 첫 주장 채점·정리 채점·리포트는 세션의 sid로 세션 한도에 포함된다.
  - 요금제 문구의 한도 수치는 이 파일에서 자동으로 따라온다(`shared/plans.ts`).
- **수용 기준**
  - 사용자는 한도를 넘으면 오늘 더 쓸 수 없다는 안내와 다음 행동을 본다.
  - 운영자는 사용자 1명이 하루에 쓸 수 있는 호출 수에 상한이 있음을 보장받는다.
  - 사용자는 계정 삭제 후 재가입으로 한도를 초기화할 수 없다(같은 날).
- **코드 경로**: `shared/quotas.ts`, `server/logos/quota.ts`, `supabase/migrations/20261013000200_usage_events.sql`, `…0400_quota_carryover.sql`.
- **상태**: 구현됨

### R9-F2 요청 가드(Origin·본문·레이트)
- **누가-왜-무엇을**: 서버가 허용되지 않은 출처·형식·과다 요청을 LLM 호출 전에 거른다.
- **선행 조건 / 트리거**: 모든 `/api/coach` 요청.
- **정상 결과**: ① POST만 허용 ② Origin(없으면 Referer)이 허용 목록(`ALLOWED_ORIGINS`, Vercel 도메인 변수)과 정확히 일치. localhost는 Vercel 환경이 아닐 때만 ③ IP당 10분 60회 ④ `content-type: application/json` ⑤ 본문 64KB 이하(헤더와 스트림 양쪽에서 확인) ⑥ zod strict 스키마(미지정 필드 거부, 입력 길이·배열 길이 상한) ⑦ 통과 후 인증·한도.
- **예외 처리**: 405/400/403/413/429가 각각 E7·E8·E3이다. 응답 본문은 `cache-control: no-store`. 레이트 맵은 5,000개 상한에서 만료분과 오래된 10%를 정리한다.
- **데이터 출처·저장**: 인스턴스 메모리(서버리스 인스턴스마다 따로 세고 콜드스타트 때 초기화, 즉 실제 한도보다 느슨하다. 코드 주석에 업그레이드 경로 명시).
- **권한**: 모든 요청.
- **상태 유지**: 없음.
- **정책**: 일일 한도는 R9-F1이 맡고 여기는 버스트와 비회원 진단만 막는다.
- **수용 기준**
  - 운영자는 허용되지 않은 출처의 요청이 AI 호출 전에 거부됨을 보장받는다.
  - 사용자는 정상 사용 중 레이트 제한에 걸리지 않는다(코칭 1세션이 12회를 넘게 호출하는 점을 고려해 60회로 설정).
- **코드 경로**: `server/logos/guard.ts`, `server/logos/schemas.ts`, `server/logos/handler.ts`.
- **상태**: 구현됨
