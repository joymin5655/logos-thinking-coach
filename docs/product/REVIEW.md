# LOGOS 문서 교차 검증 (REVIEW)

작성 2026-10-13 · 상태: 검증 결과 v1 (문서만 대조. 구현 코드는 FEATURE_SPEC·USER_FLOWS·IA_SCREENS 작성 때 읽은 범위까지만 근거로 삼음) · 관련 문서: [PRD](PRD.md), [FEATURE_SPEC](FEATURE_SPEC.md)(기능 ID 정본), [USER_FLOWS](USER_FLOWS.md), [IA_SCREENS](IA_SCREENS.md), [README](README.md)

## 0. 읽는 법

- 검증 대상은 `docs/product/`의 네 문서(PRD → FEATURE_SPEC → USER_FLOWS → IA_SCREENS)다. 기능 ID는 FEATURE_SPEC의 `Rn-Fm`을 정본으로 하고, 나머지 문서가 기능 이름으로 맞춰 따라간다.
- 처리 표기: **수정함** = 이번 검증에서 해당 문서를 고쳤다. **갭으로 남김** = 결정이나 확인이 필요해 문서에 갭으로 기록했다. **결정됨** = 2026-10-13 사용자 위임으로 확정하고 문서에 반영했다. 갭 번호는 FEATURE_SPEC `G`, USER_FLOWS `UF`, IA_SCREENS `S`, 목업 차이 `M`(IA_SCREENS §4.9)이다.
- 위치 표기: 문서명 + 절·기능 ID·플로우 단계. 예) `USER_FLOWS F6 단계 8`.
- 이 문서는 발견한 것만 적는다. 해당 사항이 없는 칸은 만들지 않았다.
- 승인 목업: [보드](https://claude.ai/artifact/NLGv7jYeE5ftQL57PbciK6)(2026-10-13 승인). 목업과 명세가 다른 9건은 IA_SCREENS §4.9에 모았고, 같은 날 사용자 위임으로 모두 결정됐다("결정됨, 2026-10-13, 위임"). 결정 후 Phase 2 구현이 끝났다는 보고를 받았지만 코드와 대조하지 못해 문서의 상태 라벨은 "계획"을 유지한다.

## 4. 여섯 관점 점검

각 관점에서 겹치지 않게 골랐다. 제안은 결정이 아니다.

### 4.1 비즈니스

1. 효과 검증의 판정 기준이 없다. AI-사람 채점 일치도 임계값과 A/B 차이의 유의성 기준을 채점 시작 전에 사전 등록해야 파일럿 결과를 근거로 쓸 수 있다 (PRD §11.2 #9).
2. 파일럿 표본이 40~60명이고 중도 이탈이 더해진다. 주장 범위를 "파일럿 결과"로 한정하고 효과 크기보다 방향과 정성 자료를 우선한다 (PRD §9).
3. 모집 경로, 일정, 참가 인센티브가 문서에 없다 (PRD §11.2 #17). 파일럿이 지표 계측과 같은 시기에 시작하면 사전 진단 기준이 비어 있을 수 있다.
4. 웹 푸시 제외로 재방문 트리거가 약하다. 방문 D7과 세션 D7의 차이를 지표로 확인하는 계획이 있으므로 그 해석 기준을 미리 정한다 (PRD §9).
5. 구 문서의 유료화(Pro 9,900원, Team 99,000원) 목표와 전환율 지표가 새 PRD에서 빠졌다. 의도한 제외인지 확인한다 (§6 불일치표).

### 4.2 개발

1. 새 RPC가 12개(`track`, `claim_profile`, `mark_onboarded`, `join_cohort`, `withdraw_consent`, `admin_funnel` 등)이고 기능명세에 security definer로 적혀 있다. 입력 검증·권한 검사(`is_admin()` 재검사)를 RPC마다 같은 틀로 두는 편이 안전하다 (FEATURE_SPEC R7-F2~F8).
2. 퍼널 단계의 실제 구현 이름이 미확인이다. 문서는 PRD §6.3으로 맞췄으므로 구현이 다르면 문서나 구현 중 하나를 바꿔야 한다 (R7-F3).
3. 홈 완주율(`completedAt`)과 관리자 `north_star`(`finalSummary`)가 달라지는 기간이 생긴다. 두 값을 같은 화면에서 보이지 않게 하거나 안내 문구를 둔다 (G8, S21).
4. 동의 체크 상태는 sessionStorage에 보관하기로 결정됐다 (G24 ④). sessionStorage는 탭 단위라, 로그인 중 다른 탭이나 새 창으로 열리면 동의 상태가 없다. 같은 탭에서 복원된다는 구현 보고를 코드로 확인해야 한다.
5. Vercel Hobby 서버리스 메모리 기반 IP 한도는 콜드스타트 때 초기화된다. 비용 상한은 Anthropic 지출 한도 설정이 최종 방어인데 설정 여부가 미확인이다 (G5, G21).
6. 이벤트 파기를 자동으로 돌릴 수단(예약 호출 등)이 없다. 수동 실행에 맡기면 180일 약속이 지켜지지 않을 수 있다 (a7).

### 4.3 QA

1. 수용 기준이 기능마다 있으나 파일럿 장치(교차 출제, 군 고정 배정, 철회, 블라인드 export)는 단위 규칙이 많다. "같은 코드로 재참가", "삭제 후 재참가", "철회 후 재참여" 같은 경계 사례를 시험 목록에 넣는다 (G25, USER_FLOWS F6 단계 9).
2. 교차 출제는 "재검사에서 같은 문항 금지"가 핵심이다. 진단 기록에 문항 id가 없고(언어 변경 시 매칭 불가) 문항 선택이 횟수 mod 4라 검증할 근거가 약하다 (G6).
3. 작성 비율 카드는 `finalSummary`가 있으면 항상 보이도록 바뀌었다. 코치가 던진 질문 수는 물음표 휴리스틱이라 물음표 없는 질문이나 물음표가 든 비질문 문장을 틀리게 셀 수 있다. 한국어 어절 특성상 겹침이 거의 0%로만 나오는지도 파일럿 데이터로 점검한다 (G13).
4. 목업 샘플 점수는 유효값(15/30 · 30/40 · 15/30, 총점 60, +15)으로 고쳤다고 보고받았다 (M5). 리포트 실제 화면의 점수 표기가 루브릭 단계(5점 단위)를 벗어나지 않는지 시험에 포함한다.
5. 자동 접근성 검사와 성능 측정이 CI에 있는지 미확인이다 (G19).
6. 이 문서들은 코드를 실행하지 않고 읽어서 작성했다. 레이아웃·동작은 실행 확인 전이다 (IA_SCREENS "구현 확인 범위와 한계").

### 4.4 UX

1. 한도를 쓴 글을 보낸 뒤에야 알게 된다. 남은 횟수 표시와 시작 시점 안내가 없어 좌절과 미완주 기록이 생긴다 (UF4, S5).
2. 한도 사유(하루/세션당)를 구분하지 않아 "내일 다시"가 틀릴 수 있다 (UF5).
3. 처음 온 사용자의 빈 상태 설명이 없다. 빈 상태 문구 키는 사전에 있으나 화면에서 쓰이지 않는다 (S1). `/welcome` 온보딩이 이 문제를 일부 줄인다.
4. 성장 체감은 완주 2회 이상이어야 추이가 보인다. 그 전의 빈 시간을 주간 리캡·마일스톤이 메우려면 0건·1건일 때의 표시를 정해야 한다 (S19, 목업에는 활동이 있는 상태만 있음).
5. 스트릭 위험 배너는 수동 쉬어가기 없이 [시작]·[닫기]만 두기로 결정됐다 (M1). 남은 쉬어가기 수와 자정까지 남은 시간이 기기 시각 기준이라 서버 KST 날짜와 어긋날 수 있는 경계(자정 전후)를 시험 목록에 넣는다 (G9).
6. 모바일에서 3분 진단이 "더보기" 안에 있어 첫 기준점 접근이 어렵다 (S9).

### 4.5 디자인

1. `/join` 문구는 "코칭 대화 내용은 연구 분석에 쓰지 않아요(채점에는 진단 글만 써요)"로 고쳐 사실과 맞췄다 (M6). 이 문장이 계속 사실이려면 블라인드 export(`admin_rater_export`)가 진단 글만 내보내야 한다. 이후 기능 추가 때 이 약속이 깨지지 않게 export 범위를 시험에 고정한다.
2. `/join` 동의 체크박스는 기본 해제로 정해졌다 (M6). "두 그룹 중 하나에 배정돼요" 문구는 설명 동의에 필요해 유지하기로 했다(2026-10-13, 위임). 군 존재를 알리면 B군의 행동이 바뀔 수 있으므로, 참가자는 자기 군을 볼 수 없게 했다(`arm` 열 select 제외, R7-F6).
3. 작성 비율 카드의 반사실 문장은 단정을 피한 문장("보통의 AI 대화라면 답이나 목록을 먼저 받는 경우가 많아요.")으로 대체했다 (M4). "코치가 준 답" 칸을 뺐으므로 세 칸은 질문 수·직접 쓴 글자 수·겹침 비율이다.
4. `/admin` 퍼널·군별 섹션은 목업이 없다. 기존 `/admin` 스타일을 따른다고만 정했으므로 표본이 작을 때의 "n<5" 표시 방식을 같이 정한다 (IA §4.7).
5. 오류 표시 방식(`ErrorLine` 대 일반 문단)이 화면마다 다르다 (S17).
6. 마일스톤 "다음 목표" 힌트는 루브릭 설명형 문구로 하고 내용에 대한 조언이 아니라고 정했다 (M3). 힌트 문구가 실제로 조언처럼 읽히지 않는지 문구 단위로 검수한다.

### 4.6 보안

1. 블라인드 export는 `blind_id`·`form`·`text`만 내보내지만, `text` 안의 이름·이메일 같은 개인정보는 걸러지지 않는다. CSV 보관·폐기 기준도 없다 (G16).
2. `track` RPC는 비회원도 호출한다. 위조·중복·대량 호출을 막는 방법(속도 제한, props 검증)이 명세에 있는지 확인이 필요하다. 문자열 32자 상한과 열거형 제한은 있으나 호출 빈도 제한은 미확인이다 (R7-F2).
3. `join_cohort`의 코호트 코드는 여러 사람이 공유하는 값이다. 유출되면 누구나 참가할 수 있고, 시도 횟수 제한은 명세에 없다 (R7-F6).
4. 삭제 요청으로 지워지지 않는 데이터가 있다: 로그인 전 `anon_id` 이벤트 (G26), 이미 내보낸 CSV (USER_FLOWS F6 단계 9), 백업(미확인). 처리방침에 적을 문구를 정해야 한다.
5. `delete_my_account`가 호스팅 Supabase에서 어떻게 동작하는지 검증하지 않았다 (G21). 삭제 약속이 있는 이상 시험이 필요하다.
6. 처리방침·이용약관은 법률 검토를 거치지 않았다(초안 배지는 제거, `/terms`는 구현됨). 이벤트 수집·파일럿 동의는 방침에 아직 없다. 계측 배포와 방침 갱신을 같이 해야 한다 (G14, S11, PRD §9).

## 7. 확인하지 못한 것

- 구현 코드를 새로 읽지 않았다. 병합된 main이 문서 작성 기준 커밋과 다른지는 일부 항목(`verdictOf`, 아레나 주제 6개, 예시 버튼)만 재확인했다.
- 구현은 끝났다는 보고를 받았다(이벤트 이름, `Join.tsx`의 sessionStorage 보관, 체크박스 기본 해제, 목업 샘플 점수 수정 등). 이 보고의 내용은 코드와 대조하지 못했다. 이벤트 props와 `session_complete`의 발생 조건, 체크 상태 복원 동작, 마일스톤 NEW 확인 값의 저장 위치, 배너 닫음 키 이름은 미확인이다. `delete_my_account`의 호스팅 Supabase 동작도 미확인이다.
- 처리방침·약관은 법률 검토를 거치지 않았다. 이 문서의 개인정보 항목은 제품 관점의 점검이지 법적 판단이 아니다.
- 팀 컨텍스트 v5.0의 인용 연구(MIT, Microsoft)는 원문과 대조하지 않았다 (PRD §11.2 #15).
- 승인 목업은 보드의 화면 구성을 읽고 대조했다. 목업의 모든 상태(빈 상태, 오류 상태)를 확인한 것은 아니다.
- 이 문서의 플로우 다이어그램(Mermaid)은 괄호·따옴표 균형만 점검했고 렌더 확인은 하지 못했다(`mmdc` 미설치).
